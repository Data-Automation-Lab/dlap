# Event-Driven Architecture with Kafka

## Overview

DADiscovery utilizes an event-driven architecture (EDA) powered by Apache Kafka to decouple various components and enable asynchronous processing. This approach enhances scalability, resilience, and flexibility, particularly for resource discovery, log analysis, and metrics collection.

The system relies on publishing specific events (`ResourceEvent`, `LogEvent`) to Kafka topics. Dedicated listeners consume these events and delegate processing to a chain of registered event processors (`IEventSubscriber` implementations managed by `EventProcessorRegistry`).

## Benefits

-   **Decoupling**: Producers (e.g., `IResourceCrawler`, `ILogAnalyzer`) are decoupled from consumers (event processors like catalog updaters, metrics collectors).
-   **Asynchronous Processing**: Long-running tasks like discovery or analysis don't block core application threads. Work is performed asynchronously, often triggered by events.
-   **Scalability**: Kafka allows producers and consumers to scale independently. Multiple instances of listeners or processors can be deployed.
-   **Resilience**: Kafka acts as a durable message buffer, ensuring events aren't lost if consumers are temporarily unavailable.
-   **Extensibility**: New functionality (e.g., new types of analysis, notifications) can be added by creating new `IEventSubscriber` implementations without modifying existing producers or processors.
-   **Observability**: Centralized event streams can be monitored and audited.

## Design Goals and Evolution (Refactoring Context)

The move to this event-driven model was driven by the need to:
1.  Make core components like `IResourceCrawler` and `ILogAnalyzer` stateless and non-blocking.
2.  Eliminate direct dependencies between resource/log producers and their consumers (catalog, metrics, etc.).
3.  Enable flexible, independent processing of discovery and log analysis results.

### Original Interface Changes

During the refactoring, key interfaces were modified to support asynchronous, event-based operations:

*   **`IResourceCrawler`**: Methods like `discoverResources` were adapted to become asynchronous (e.g., `discoverResourcesAsync`), returning `void` and publishing `ResourceEvent`s instead of returning lists of resources directly.
*   **`ILogAnalyzer`**: Methods like `analyzeLogsBetween` and `analyzeLogEvent` were similarly adapted (e.g., `triggerLogAnalysisAsync`, `processLogEventAsync`), returning `void` and publishing `LogEvent`s containing `ResourceChange` payloads.

## Core Components

1.  **Kafka**: The message broker used for transporting events.
2.  **Events**:
    *   `com.dalab.discovery.sd.event.type.ResourceEvent`: Represents a resource discovery or change (e.g., CREATE, UPDATE, DELETE) typically generated by `IResourceCrawler` implementations.
    *   `com.dalab.discovery.sd.event.type.LogEvent`: Represents a resource change detected via log analysis, typically generated by `ILogAnalyzer` implementations. It usually contains a `ResourceChange` payload.
3.  **Producers**: Components that generate and send events to Kafka topics. This is often handled within `IResourceCrawler` or `ILogAnalyzer` implementations using an injected `KafkaTemplate`.
4.  **Consumers (Listeners)**:
    *   `ResourceEventListener`: Listens on the `discovery-resource-events` topic using `@KafkaListener`.
    *   `LogEventListener`: Listens on the `discovery-log-events` topic using `@KafkaListener`.
    *   Both listeners delegate processing to the `EventProcessorRegistry`.
5.  **`EventProcessorRegistry`**: A service that discovers all beans implementing `IEventSubscriber<ResourceEvent>` or `IEventSubscriber<LogEvent>` at startup. It sorts them by priority and provides lists of relevant processors to the listeners.
6.  **Event Processors (`IEventSubscriber<T>`)**: Implementations that contain specific business logic to handle events. Examples include:
    *   `CatalogResourceEventProcessor`: Updates the internal catalog based on `ResourceEvent`s.
    *   `CatalogLogEventProcessor`: Updates the internal catalog based on `LogEvent`s (processing the `ResourceChange` payload).
    *   `UnifiedResourceMetricsProcessor`: Collects and persists metrics from `ResourceEvent`s.
    *   `UnifiedLogMetricsProcessor`: Collects and persists metrics from `LogEvent`s.

## Configuration

### 1. Dependencies

Ensure `spring-kafka` is included in `build.gradle.kts`.

### 2. Kafka Properties (`application.yml` or `application.properties`)

Key properties are configured, often with defaults set in `KafkaConfiguration.java`:

```yaml
kafka:
  bootstrap-servers: ${KAFKA_BROKERS:localhost:9092} # Use environment variable or default
  topics:
    resource-events: discovery-resource-events
    log-events: discovery-log-events
  # Consumer group ID shared by listeners
  group:
    catalog-updater: discovery-processor-group # Example group ID

# Spring Kafka properties (optional overrides)
spring:
  kafka:
    bootstrap-servers: ${kafka.bootstrap-servers}
    consumer:
      group-id: ${kafka.group.catalog-updater}
      auto-offset-reset: earliest
      # Consider adding trusted packages if complex types cause issues
      # properties:
      #  spring.json.trusted.packages: com.dalab.discovery.sd.domain.model,com.dalab.discovery.sd.event.type.*
    producer:
      key-serializer: org.apache.kafka.common.serialization.StringSerializer
      value-serializer: org.springframework.kafka.support.serializer.JsonSerializer
      properties:
        # Reliability settings (defaults set in KafkaConfiguration)
        # acks: all
        # retries: 3
```

### 3. Enabling Kafka and Async

The `@EnableKafka` and `@EnableAsync` annotations are typically present on a configuration class like `KafkaConfiguration` to activate Kafka listeners and asynchronous processing (`@Async` methods used by producers/processors).

## Event Flow

1.  An `IResourceCrawler` discovers a new resource.
2.  It constructs a `ResourceEvent` with the resource details and `ChangeType.CREATE`.
3.  It uses `KafkaTemplate.send("discovery-resource-events", event)` to publish the event.
4.  The `ResourceEventListener` consumes the event from the topic.
5.  The listener asks `EventProcessorRegistry` for processors capable of handling this `ResourceEvent`.
6.  The registry returns a list of relevant `IEventSubscriber<ResourceEvent>` beans (e.g., `CatalogResourceEventProcessor`, `UnifiedResourceMetricsProcessor`), sorted by priority.
7.  The listener iterates through the processors, calling `processor.process(event)` on each.
8.  Each processor executes its specific logic (updating the catalog, recording metrics, etc.).
9.  A similar flow occurs for `LogEvent`s generated by `ILogAnalyzer` implementations, consumed by `LogEventListener`, and processed by `IEventSubscriber<LogEvent>` implementations.

## Troubleshooting

### Common Issues

1.  **Events Not Processed**:
    *   Verify Kafka brokers are running and accessible (`kafka.bootstrap-servers`).
    *   Check listener logs (`ResourceEventListener`, `LogEventListener`) for connection errors or consumption issues.
    *   Ensure the consumer group (`kafka.group.catalog-updater`) is correctly configured.
    *   Confirm producer code is actually sending messages (add logging).
2.  **Serialization/Deserialization Errors**:
    *   Ensure event classes (`ResourceEvent`, `LogEvent`) and their payloads (`CloudResource` subclasses, `ResourceChange`) are correctly serializable/deserializable (e.g., have default constructors, necessary annotations like `@JsonTypeInfo` if polymorphism is used).
    *   If using complex types, you might need to configure `spring.kafka.consumer.properties.spring.json.trusted.packages`.
3.  **Processors Not Running**:
    *   Verify the processor class is annotated with `@Component` (or another stereotype) and implements the correct `IEventSubscriber<T>` interface.
    *   Check `EventProcessorRegistry` logs at startup to confirm it's discovering and registering the processor.
    *   Ensure the `canProcess` method in the processor returns `true` for the relevant events.
4.  **Incorrect Processing Order**:
    *   Review and adjust the `getPriority()` values in `IEventSubscriber` implementations (lower numbers run first).

### Logging

Enable DEBUG logging for relevant components in your logging configuration (`logback-spring.xml` or `application.yml`):

```yaml
logging:
  level:
    com.dalab.discovery.sd.event: DEBUG # For listeners and registry
    com.dalab.discovery.sd.event.processor: DEBUG # For specific processors
    org.springframework.kafka: INFO # Or DEBUG for more verbose Kafka client logging
    org.apache.kafka.clients: INFO
```

### Monitoring Kafka Topics

Use standard Kafka command-line tools to inspect topics:

```bash
# List topics
kafka-topics --bootstrap-server localhost:9092 --list

# Consume messages from resource events topic
kafka-console-consumer --bootstrap-server localhost:9092 --topic discovery-resource-events --from-beginning --property print.key=true

# Consume messages from log events topic
kafka-console-consumer --bootstrap-server localhost:9092 --topic discovery-log-events --from-beginning --property print.key=true
```
